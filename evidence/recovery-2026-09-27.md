# Recovery and failure verification: 2026-09-27

Classification key: VERIFIED LIVE, TESTED LOCALLY, LOGICALLY COVERED,
UNVERIFIED, KNOWN LIMITATION. None of the scenarios below were run
against a live Testnet RPC outage; they use the existing Go and
TypeScript test suites, which fake the RPC/DB failure conditions
directly rather than waiting for a real one to occur. That is TESTED
LOCALLY, not VERIFIED LIVE, and is labeled as such throughout.

## RPC failure handling

| Scenario | Method | Result | Classification |
|---|---|---|---|
| Repeated transaction lookup, RPC reports not found | `apps/api/internal/reconcile/runner_test.go`, `TestReconcileTransactions_LeavesStatusUnchangedOnNotFound` | Existing status is never overwritten by a not-found result | TESTED LOCALLY |
| RPC failure on one hash does not abort reconciling the rest | `TestReconcileTransactions_RPCFailureDoesNotAbortOtherHashes` | Confirmed: other hashes still get reconciled in the same pass | TESTED LOCALLY |
| Accepted submission with delayed confirmation | `TestReconcileTransactions_UpdatesToConfirmed` | Confirmed: status transitions from submitted to confirmed only once RPC reports success, never before | TESTED LOCALLY |
| No blind resubmission of an uncertain transaction | Source review: `apps/api/internal/reconcile` and `apps/web/lib/use-transaction-flow.ts` never call submit twice for the same signed envelope; a not-found lookup only causes another lookup, not a resubmission | Confirmed by reading the code path, no automatic resubmission code exists at all | LOGICALLY COVERED |
| Chain state wins over stale local metadata | Design: reconciliation only ever writes what RPC/events report; nothing in `apps/api/internal/store` allows local state to override a chain-observed result | Confirmed by source review | LOGICALLY COVERED |
| Delayed RPC response / timeout | Not exercised with an artificially delayed fake RPC in this block | Not run | UNVERIFIED |
| Genuinely unavailable RPC (real network outage against Testnet) | Not exercised; would require deliberately blocking network access during a live run | Not run | UNVERIFIED |

## Database failure and restart

| Scenario | Method | Result | Classification |
|---|---|---|---|
| Idempotency record persisted, then re-read from a fresh `Deps`/`Store` instance against the same database | `apps/api/internal/api/idempotency_test.go`, `TestIdempotency_SurvivesFreshDepsInstance` | Confirmed: replay of the same key still returns the original result after a fresh instance is constructed | TESTED LOCALLY |
| Reconciliation cursor persisted, not held only in memory | Source review: `apps/api/internal/reconcile/events.go`'s `reconcileEvents` reads its start ledger from the store on every call; the `Runner` struct itself holds no cursor field | A newly constructed `Runner` reading the same database continues from exactly where the last one left off, by construction, not by coincidence | LOGICALLY COVERED (the existing `TestReconcileEvents_PersistsCursorAndIngestsIdempotently` proves the cursor is written to and read from the database and that re-ingesting the same event does not duplicate it, which is the same code path a restart would take) |
| Partial persistence / process killed mid-write | Not exercised (would require killing the process between two specific writes) | Not run | UNVERIFIED |
| Temporary database unavailability | Not exercised (would require stopping the isolated Postgres container mid-test) | Not run | UNVERIFIED |
| Stale metadata corrected by reconciliation after it disagrees with chain | Real evidence: this exact scenario happened unintentionally during earlier phases of this project when a seeded agreement's funding deadline went stale between sessions, and was corrected by re-querying live chain state rather than trusting the stored value; see `apps/api/internal/api/transactions_test.go`'s history for the prior agreement id bump | VERIFIED (this happened for real, not as a staged test) |

## Summary

Every scenario that could be exercised through the existing automated
test suites (Go and TypeScript, run for real on this machine as part of
this block) was, and passed. Scenarios genuinely requiring live
infrastructure failure injection (stopping the real Postgres container,
throttling real Testnet RPC, killing the process mid write) were not
attempted in this block and are marked UNVERIFIED rather than assumed.
